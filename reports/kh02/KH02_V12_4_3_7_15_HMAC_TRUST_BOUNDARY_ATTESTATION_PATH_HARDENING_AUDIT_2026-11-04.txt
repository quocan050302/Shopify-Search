2. ARCHITECTURAL VULNERABILITIES & PRODUCTION CODE FIXES (V12.4.3.7.15)
------------------------------------------------------------------------------------------
[P0-A] Exported Live Attestation Issuer & Circular Minting Elimination
- Root Cause:
  `issueTrustedTransportAttestation` was publicly exported and accepted caller-supplied parameters
  (rawBytes, receiptId, attemptId, endpoint, status, isTestSimulation? defaulting to false).
  Any external caller or test utility could invoke it to mint `captureMethod: "NATIVE_HTTPS_FETCH"`
  and `testOrSimulated: false` attestations without proving actual transport execution by a live collector.
- Code Fix:
  1) Public Issuer Demotion: `issueTrustedTransportAttestation` is permanently demoted to only mint
     `captureMethod: "SIMULATED_TEST_TRANSPORT"` and `testOrSimulated: true`. It is blocked from ever
     registering into `trustedInvocationsRegistry` or minting live origin claims.
  2) Private Collector-Bound Issuer: Created private `mintInternalLiveTransportAttestation(params, invocationProof)`
     inside `temporalDemandEngine.ts`. It strictly requires an active, non-simulated `TrustedInvocationProof`,
     verifies the endpoint against the allowlist (`https://serpapi.com/search.json`), and signs only with
     a genuine production key.
  3) Production Transport Binding: `executeTrustedSerpApiDemandRequest` directly calls
     `mintInternalLiveTransportAttestation` immediately after receiving a real HTTP Response, binding
     the exact attemptId, raw SHA-256, HTTP status, endpoint, and invocation proof.

[P0-B] Secret Isolation & Test Key Guarding
- Root Cause:
  `getProvenanceSigningKey()` exported the raw signing secret, and `setProvenanceSigningKeyForTest()`
  allowed arbitrary callers to set in-memory signing keys without checking environment boundaries.
  Test-signed attestations could potentially be passed off as live origin evidence.
- Code Fix:
  1) Production Secret Isolation: `setProvenanceSigningKeyForTest` immediately throws `SECURITY_VIOLATION`
     if `NODE_ENV === "production"`.
  2) Non-Leaking Key Inspection: Public `getProvenanceSigningKey()` returns `{ keyConfigured, keyId, isTestKey }`
     without exposing the raw secret string. Secret access is restricted to private `getInternalProvenanceSigningSecret()`.
  3) Fail-Closed Test Key Demotion: In `verifyDurableTransportAttestation` and `resolveVerifiedDemandEvidence`,
     when `strictLiveOrigin: true` is requested, attestations signed with test keys (`test_key_v1` or
     `isTestKey: true`) are strictly rejected with `ORIGIN_UNVERIFIED` and `eligible: false`.

[P1-C] Attestation Storage Path Sanitization & Symlink / Conflict Protection
- Root Cause:
  Attestation persistence and loading used raw `receiptId` strings in file path construction without
  sanitization, exposing the system to directory traversal (`../`), symlink following, or Windows device names.
- Code Fix:
  1) Strict Attestation ID Validation: `validateAndSanitizeAttestationId` allows only `[a-zA-Z0-9_-]{1,128}`
     and explicitly rejects path separators (`/`, `\`), traversal (`..`), colons, control characters,
     and reserved Windows device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`).
  2) Path Traversal & Symlink Guarding: `resolveSafeAttestationPath` verifies that the resolved path stays
     strictly inside the canonical attestation directory. `lstatSync` is used to detect and reject symlinks.
  3) Atomic Multi-Process Persistence: `persistTransportAttestationAtomically` acquires an exclusive file lock,
     performs deep identity conflict checks against existing files (comparing raw SHA-256, upstream ID,
     capture method, and signature), writes atomically to a `.tmp` file with `fsync`, and renames into place.

[P1-D] Canonical Serialization Schema 2.0 Injective Encoding
- Root Cause:
  Schema 1.0 used pipe-delimited (`|`) field concatenation, which was theoretically susceptible to delimiter
  injection if field values contained pipe characters.
- Code Fix:
  1) Domain Separator: Schema 2.0 uses domain separator `SWAI_KH02_ATTESTATION_V2\n`.
  2) Injective Length-Prefixed Serialization: Encodes fields with explicit length prefixes:
     `${k.length}:${k}=${vBuf.length}:${v}\n` with sorted keys and Unicode NFC normalization.
  3) Constant-Time Verification: Signatures are verified using `crypto.timingSafeEqual` over 64-hex SHA-256 HMACs.
  4) Backward-Compatible Parsing: Legacy Schema 1.0 remains readable for historical replay, but Schema 2.0
     is strictly required for all new attestations and mandatory under `strictLiveOrigin: true`.

[P1-E] Fail-Closed Business Gates (G06, G07, G15, G16)
- Guarantees:
  Zero false PASS. Offline, test-signed, or simulated attestations are permanently blocked from elevating
  business gates G06 (Google Ads), G07 (TikTok Ads), G15 (Longitudinal Demand), and G16 (Top-3 Winning Products).
  All missing or test-key receipts resolve to `ORIGIN_UNVERIFIED`, `INSUFFICIENT_HISTORICAL_EVIDENCE`, or `BLOCKED`.

[P1-F] Harness Synchronization & Multi-Process Verification
- Code Fix:
  `tests/support/kh02TestProvenanceHarness.ts` updated to construct valid Schema 2.0 attestations signed with
  explicit test key `test_key_v1`. Multi-process concurrency tests (T26, T27) verified real OS child processes
  safely persist attestations under atomic locking with zero lost updates.

4. REALISTIC CRYPTOGRAPHIC THREAT BOUNDARY DEFINITION
------------------------------------------------------------------------------------------
- Threat Boundary Definition:
  A cryptographic HMAC establishes integrity and provenance ONLY relative to the entity holding the
  signing key. An attestation signed with a test key (`test_key_v1`) proves internal format correctness,
  recovery determinism, and tamper-evident storage, but CANNOT independently attest that a remote
  third-party server was contacted.
- Production Security Boundary:
  1) Public callers and untrusted input cannot mint LIVE-origin attestations.
  2) Live attestations are strictly collector-bound and minted only via private `mintInternalLiveTransportAttestation`
     guarded by an active, unexpired `TrustedInvocationProof` and endpoint allowlist.
  3) In production environments (`NODE_ENV === "production"`), test keys cannot be configured.
  4) Under `strictLiveOrigin: true`, test keys and simulated capture methods are rejected fail-closed.
  5) Business gates G06, G07, G15, and G16 remain blocked/insufficient in the absence of genuine live tokens.
