2. ARCHITECTURAL VULNERABILITIES & PRODUCTION CODE FIXES (V12.4.3.7.14)
------------------------------------------------------------------------------------------
[P0-A] Test Simulation Proof Isolation & Production Transport Boundary
- Root Cause:
  In previous iterations, test harnesses could mint synthetic proofs using general-purpose helper
  functions that were structurally indistinguishable from live production transport receipts, or
  unit tests could inadvertently grant `ACTUAL_PROVIDER_INVOCATION` authority to simulation data.
- Code Fix:
  1) Explicit Proof Separation: Public token creation and test utilities strictly produce `TEST_SIMULATION`
     proof tokens with `isTestSimulation: true`. They can never mint `LIVE_ORIGIN` tokens.
  2) Persistence Fencing: When `persistCollectorReceiptAtomically()` encounters a `TEST_SIMULATION` proof,
     it automatically demotes the stored `originKind` to `SIMULATED_TRANSPORT`, forces `originVerified = false`,
     and blocks live promotion.
  3) Production Import Guard: Test harness functions were moved to `tests/support/kh02TestProvenanceHarness.ts`
     and protected with a runtime guard throwing an error if imported from any production module under `src/`.

[P0-B] Durable HMAC-SHA256 Signed Transport Attestations (Anti-Circular Minting)
- Root Cause:
  Recovery mechanisms (`reconcilePendingReceiptRecovery`) previously inspected unsigned ledger JSON fields
  on disk and risked circular proof creation where an attacker modifying the JSON could mint live authority.
- Code Fix:
  1) `ProviderTransportAttestationV1` schema introduced, featuring cryptographic HMAC-SHA256 signature
     over canonical JSON payload serialization (`computeCanonicalAttestationPayload`).
  2) Attestation files (`${receiptId}.attestation.json`) are written atomically with sync and fsync.
  3) `verifyDurableTransportAttestation` validates issuerKeyId, signature validity using constant-time
     comparison (`crypto.timingSafeEqual`), payload raw SHA-256 match, upstreamRequestId match, provider match,
     and allowlist endpoints (`https://serpapi.com/search.json`).
  4) `reconcilePendingReceiptRecovery` requires a valid durable attestation on disk before honoring any live
     origin claims. If corrupted or missing, the receipt is demoted to `LOCAL_INTEGRITY_ONLY`.

[P0-C] Durable Provenance Recovery Across Process Restarts & Worker Spawns
- Root Cause:
  In-memory registries (`trustedInvocationsRegistry`) were lost across process boundaries, child OS worker
  spawns, or cold server restarts, forcing consumers to fall back to unverified states.
- Code Fix:
  1) Implemented `loadDurableTransportAttestationSync` and `loadDurableTransportAttestation` to load signed
     attestation artifacts from disk.
  2) Cold recovery (`reconcilePendingReceiptRecovery`) verifies the cryptographic attestation on disk and
     repopulates memory structures safely.
  3) Multi-process safety: verified through child Node processes that authentic attestations persist across
     process lifecycles while forged attestations remain strictly blocked.

[P0-D] Canonical Verifier & Timeline Point Date/Value Parity Verification
- Root Cause:
  Canonical verification (`verifyReceiptEligibility` / `resolveVerifiedDemandEvidence`) checked SHA-256
  and HTTP status but did not rigorously enforce that requested observation dates and values matched
  exact points in the provider's raw `timeline_data`.
- Code Fix:
  1) Date & Value Parity: If `context.observationDate` is supplied, `resolveVerifiedDemandEvidence` looks up
     the matching point in `interest_over_time.timeline_data`. If not found, it rejects with `DATE_MISMATCH`.
     If value does not match `context.observationValue`, it rejects with `HASH_MISMATCH`.
  2) Point-in-Time Constraint: If `context.asOfTimestamp` is provided, observations occurring after the cutoff
     or receipts captured after cutoff are rejected with `POINT_IN_TIME_VIOLATION`.
  3) Universal Fail-Closed Origin: All error rejection branches explicitly return `verifiedOrigin: false`
     and `eligible: false`.
