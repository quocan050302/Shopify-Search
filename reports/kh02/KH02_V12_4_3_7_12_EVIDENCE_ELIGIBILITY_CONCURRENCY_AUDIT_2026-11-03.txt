[P0-1] Ledger Receipt Written Before DB Commit Becomes Evidence-Eligible Too Early
- File & Lines: src/services/kh02/demand/temporalDemandEngine.ts:722-785, 810-915, 1052-1193, 1215-1660
- Root Cause:
  1) finalizeProviderInvocationFromTransport() and recordTrustedProviderInvocation() previously populated
     in-memory trusted caches and wrote ledger records without awaiting SQLite ResearchEvidence persistence.
  2) persistDurableReceipt() wrote ledger entries that getTrustedProviderReceipt() and
     isAuthenticProviderReceiptDescriptor() treated as verified even when dbCommitted === false or when
     persistCollectorReceiptAtomically() failed at the database stage.
- Code Fix:
  1) Introduced strict ReceiptCommitState lifecycle on ProviderInvocationReceipt:
     "LEDGER_PENDING_DB" | "EVIDENCE_ELIGIBLE" | "DB_WRITE_FAILED" | "DB_READBACK_FAILED" |
     "HASH_MISMATCH" | "CONFLICT" | "LOCK_TIMEOUT" | "RECOVERY_REQUIRED" | "FAILED".
  2) Synchronous functions (finalizeProviderInvocationFromTransport, recordTrustedProviderInvocation,
     persistDurableReceipt) ONLY stage commitState = "LEDGER_PENDING_DB" with eligible = false and
     verifiedAt = null, and explicitly remove any stale entry from in-memory eligible caches.
  3) persistCollectorReceiptAtomically() implements a 4-stage Compare-And-Swap (CAS) commit:
     Stage 1: Verify physical artifact on disk (path confinement, no symlinks, non-empty, 64-hex SHA-256,
              valid JSON without upstream error).
     Stage 2: Acquire ledger lock, check full metadata conflict, write LEDGER_PENDING_DB (eligible=false)
              via write-temp-fsync-rename, verify disk readback, and release ledger lock.
     Stage 3: Acquire DB serialization lock, await prisma.researchEvidence.upsert(), and await
              prisma.researchEvidence.findUnique() readback verifying id, sourceContentRef === normSha,
              and observedValue JSON parity. On any DB write/readback failure, transition ledger entry to
              DB_WRITE_FAILED or DB_READBACK_FAILED with eligible=false and return immediately.
     Stage 4: Re-acquire ledger lock, verify generation/hash CAS invariant, transition ledger entry to
              commitState = "EVIDENCE_ELIGIBLE", eligible = true, verifiedAt = ISO timestamp, fsync+rename,
              verify disk readback, and only then populate trustedInvocationLedger.

[P0-2] resolveVerifiedDemandEvidence Trusts Ledger Without DB Readback When dbCommitted Is False/Failed
- File & Lines:
  * src/services/kh02/demand/temporalDemandEngine.ts:2245-2650, 2670-3080
  * src/services/kh02/demand/historicalDemandIngestion.ts:275-315, 415-465
- Root Cause:
  resolveVerifiedDemandEvidence() previously accepted receipts found in the ledger file without verifying
  that a matching ResearchEvidence record was committed in SQLite, and without requiring
  commitState === "EVIDENCE_ELIGIBLE" && eligible === true.
- Code Fix:
  1) getTrustedProviderReceipt() and findTrustedReceiptByHash() filter out any receipt where
     commitState !== "EVIDENCE_ELIGIBLE" or eligible !== true (normalizing legacy records lacking
     explicit eligibility fields to RECOVERY_REQUIRED / eligible=false).
  2) isAuthenticProviderReceiptDescriptor() enforces ledger eligibility, physical artifact existence and
     byte-level SHA-256 parity, semantic payload checks (search_metadata.status === "Success", geo/query
     alignment), and observation timeline point value membership.
  3) resolveVerifiedDemandEvidence() requires BOTH:
     - A durable ledger entry with commitState === "EVIDENCE_ELIGIBLE" && eligible === true, AND
     - A verified SQLite prisma.researchEvidence.findUnique({ where: { id: receiptId } }) row whose
       sourceContentRef and observedValue.rawResponseSha256 match the ledger SHA-256 and physical file
       SHA-256 on disk.
     DB-only forgeries fail with ORIGIN_UNVERIFIED; ledger-only forgeries fail with DB_RECORD_MISSING;
     uncommitted/pending receipts fail with RECEIPT_NOT_ELIGIBLE.

[P1-4] Lock File Release & Stale Reclamation Race Conditions
- File & Lines: src/services/kh02/demand/temporalDemandEngine.ts:916-1000
- Root Cause:
  1) releaseDurableLedgerLock() previously unlinked the lock file inside a catch block if JSON parsing
     failed (e.g., while another process was writing or on corrupted lock content).
  2) Stale lock reclamation unlinked and re-created the lock file in two non-atomic steps and did not
     strictly prevent stealing an expired lease whose owner PID was still alive on the same host.
- Code Fix:
  1) releaseDurableLedgerLock() never unlinks on JSON parse error, symlink, missing ownerId, or
     ownerId/PID mismatch.
  2) When an existing lock's expiresAt has passed, isProcessAliveOnSameHost(pid, hostname) checks
     process.kill(pid, 0). If the owner PID is still alive, the lock is NEVER stolen and the contender
     fails closed with LOCK_TIMEOUT.
  3) If the owner PID is confirmed dead, tryReclaimDeadExpiredLockAtomically() renames the lock file to
     a temporary claim path, re-verifies that ownerId did not change during the rename, and unlinks the
     claim file before retrying O_CREAT | O_EXCL acquisition.

3. RECEIPT COMMIT STATE MACHINE & CROSS-STORE COORDINATION BOUNDARIES
------------------------------------------------------------------------------------------
State Machine Transitions:
  NEW_ATTEMPT
    -> TRANSPORT_RESPONSE_200 (HTTP 200 + valid JSON + search_metadata.id + status="Success")
    -> RAW_ARTIFACT_VERIFIED (64-hex SHA-256 content-addressed file written & verified on disk)
    -> LEDGER_PENDING_DB (staged under .lock via temp+fsync+rename; eligible=false, dbCommitted=false)
    -> DB_COMMITTED (Prisma ResearchEvidence upsert awaited under .db.lock)
    -> DB_READBACK_VERIFIED (Prisma findUnique readback verified for id, sourceContentRef, observedValue)
    -> EVIDENCE_ELIGIBLE (CAS transition under .lock; eligible=true, dbCommitted=true, verifiedAt!=null)

Failure & Recovery Terminal States:
  - LOCK_TIMEOUT (eligible=false, dbCommitted=false)
  - MISSING_ARTIFACT / HASH_MISMATCH (eligible=false, dbCommitted=false)
  - CONFLICT / RECEIPT_CONFLICT (eligible=false, dbCommitted=false; original record preserved)
  - DB_WRITE_FAILED / DB_READBACK_FAILED (eligible=false, dbCommitted=false; ledger marked failed)
  - RECOVERY_REQUIRED (legacy/interrupted record; recoverable via reconcilePendingReceiptRecovery())

Honest Distributed Systems Note:
  Local POSIX/NTFS filesystem and SQLite do not share a kernel-level two-phase commit (2PC) transaction.
  This implementation guarantees zero false-positive eligibility because:
  1) Ledger staging writes LEDGER_PENDING_DB with eligible=false BEFORE SQLite upsert.
  2) Readers (getTrustedProviderReceipt, isAuthenticProviderReceiptDescriptor, resolveVerifiedDemandEvidence)
     reject any receipt unless BOTH the ledger entry has commitState="EVIDENCE_ELIGIBLE" (eligible=true)
     AND the SQLite ResearchEvidence row exists with matching SHA-256.
  3) If a process crashes between Stage 2 (LEDGER_PENDING_DB) and Stage 4 (EVIDENCE_ELIGIBLE), the receipt
     remains ineligible (fail-closed) until reconcilePendingReceiptRecovery() or an idempotent retry
     completes the DB commit + readback + CAS promotion.
