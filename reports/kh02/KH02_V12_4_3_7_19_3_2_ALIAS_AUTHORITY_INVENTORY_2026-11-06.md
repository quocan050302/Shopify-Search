## 1. Architectural Overview & Security Invariant

Prior to V19.3.2, candidate alias authorization relied on in-memory caller strings (e.g., `approvedBy: "qa_principal_lead"`, `provenanceReference: "gov_decision_ref_20261106_alias_uahpet"`). Any caller could fabricate these strings to artificially bridge unverified category queries (such as `"Automatic Wet Food Cat Feeder with Cooling & Warming"`) into product-specific demand for UAHPET (`cmvsy7zqh000jp0orhypwohho`), causing false positive gate unlocks.

V19.3.2 replaces caller-fabricated strings with a cryptographically enforced, durable, and append-only alias approval ledger:
1. **Cryptographic Identity**: Every alias approval requires an HMAC-SHA256 signature generated by a registered, purpose-scoped authority key (`KH02_DEMAND_ALIAS`).
2. **Canonical Payload Serialization**: Canonicalization deterministically encodes 21 fields with domain separator `SWAI_KH02_ALIAS_APPROVAL_V1\n`. Any single-byte modification causes a `TAMPERED_PAYLOAD` rejection.
3. **Purpose Separation**: Alias authority signing keys are completely segregated from provider transport receipt keys (`KH02_PROVENANCE_SIGNING_KEY`).
4. **Durable File Ledger**: Atomic filesystem ledger persistence (`.candidate_alias_ledger.json`) with PID-aware POSIX/Windows mutex file locking (`.candidate_alias_ledger.lock`).
5. **Monotonic Revocation**: Once revoked, an approval record cannot be un-revoked or overwritten by re-persisting the unrevoked payload (`REVOKED`).
6. **Conflict & Idempotency Rules**: Identical payloads on the same `approvalId` return `IDEMPOTENT_SKIP`. Conflicting payloads on the same `approvalId` fail-closed with `CONFLICT_ERROR`.
7. **Read-Time Enforcement**: Verification strictly matches tenant (`workspaceId`), candidate (`candidateId`), product identity (`canonicalProductId`), run (`researchRunId`), region (`region`), temporal window (`effectiveAt`, `expiresAt`), point-in-time (`asOfTimestamp`), and normalized canonical queries.

## 3. Trust Registry & Key Management

- **Environment Variable Key:** `KH02_ALIAS_SIGNING_KEY` (minimum 32-character secret). Registered under keyId `alias_prod_key_v1`.
- **Key Trust Store:** `keyRegistry` map enforcing status (`ACTIVE`, `REVOKED`, `COMPROMISED`, `TEST_ONLY`).
- **Production Guard:** Throws `SECURITY_VIOLATION` if any caller attempts to register a `TEST_ONLY` key when `NODE_ENV === "production"`.
- **Compromised Key Rejection:** Any key marked `COMPROMISED` or `REVOKED` immediately causes `KEY_REVOKED` failure for existing and new alias validations.

---

## 4. Ledger Concurrency & Locking Protocol

- **Ledger Storage Path:** `data/candidate_aliases/.candidate_alias_ledger.json` (or `process.env.TEST_CANDIDATE_ALIAS_STORAGE_DIR`).
- **Mutex Lock Path:** `data/candidate_aliases/.candidate_alias_ledger.lock`.
- **Lock Format:** JSON object containing `{ ownerId, pid, hostname, acquiredAt, expiresAt }`.
- **Dead Lock Recovery:** If lock expiration has passed (`expiresAt < Date.now()`) AND `process.kill(pid, 0)` confirms the owning PID is deceased on the host, the stale lock is safely reclaimed.
- **Atomic File Write:** Writes updated state to a PID-unique temporary file (`.candidate_alias_ledger.json.tmp_<pid>_<timestamp>_<nonce>`), then atomically replaces the active ledger using `fs.renameSync`.

## 5. Candidate Attribution & Identity Binding Rules

1. **Exact Title Matching:** `EXACT_CANDIDATE_KEYWORD_MATCH` (`isAttributable: true`). Punctuation, casing, and whitespace normalization supported via `areExactOrCanonicalEquivalentQueries`.
2. **Verified Explicit Alias:** `VERIFIED_EXPLICIT_ALIAS_MATCH` (`isAttributable: true`) ONLY when backed by a verified `CandidateAliasApprovalRecord` in the durable ledger.
3. **Unbound Foreign Product Identity (A10 Fix):** When candidate has `canonicalProductId: null` and observation has an explicit foreign `productId`, observation is rejected with `KEYWORD_ONLY_UNBOUND` (`isAttributable: false`).
4. **Missing Observation Product Identity:** When candidate has `canonicalProductId` and observation has `productId: null` without authentic `evidenceReference`, observation is rejected with `INSUFFICIENT_CANDIDATE_IDENTITY` (`isAttributable: false`).
5. **Cross-Product Mismatch:** When both specify product IDs that differ, rejected with `EXCLUDED_CROSS_PRODUCT` (`isAttributable: false`).
6. **SKU Variant / Accessory Separation:** Accessories and disjoint SKU variants cannot borrow demand without explicit authorized records (`EXCLUDED_KEYWORD_MISMATCH`).
